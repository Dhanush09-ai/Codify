# Chapter 8: HTML Forms

## Section 3: Accessible Form Design

A good form should be easy for **everyone** to understand and use.

Accessible form design means creating forms that can be used by people with different abilities, including people who:

* Use screen readers
* Navigate using a keyboard
* Have difficulty seeing small text
* Have difficulty using a mouse
* Need clear instructions and error messages

> **Simple idea:** An accessible form clearly tells users what information is needed and makes it easy to enter that information.

---

## 1. Why Form Accessibility Matters

Imagine a registration form:

```text
Name:     [____________]
Email:    [____________]
Password: [____________]

          [ Register ]
```

A person looking at the screen can understand which input belongs to which label.

But a screen reader or keyboard user needs proper HTML structure to understand the same relationships.

Good HTML provides this information through:

* `<label>`
* `for`
* `id`
* Proper input types
* Clear instructions
* Semantic grouping
* Useful error messages

---

## 2. Always Use `<label>`

A `<label>` describes a form control.

Example:

```html id="1u0w6n"
<label for="name">Full Name:</label>

<input
    type="text"
    id="name"
    name="name"
>
```

The label says what information the user should enter.

Without a label:

```html id="z9y0s8"
<input type="text">
```

the purpose of the input may not be clear.

---

## 3. Connect `<label>` Using `for` and `id`

The `for` attribute of `<label>` should match the `id` of the related form control.

Example:

```html id="8g5v2p"
<label for="email">Email Address:</label>

<input
    type="email"
    id="email"
    name="email"
>
```

The connection is:

```text id="3d9h8k"
<label for="email">
          ↓
<input id="email">
```

This tells the browser that the label belongs to that input.

---

## 4. Why Label Association Is Useful

A correctly associated label can make a form easier to use.

For example:

```html id="q1x9w2"
<label for="username">Username</label>

<input
    type="text"
    id="username"
    name="username"
>
```

When the user interacts with the label, the associated input can receive focus.

This is especially useful for:

* Keyboard users
* Touchscreen users
* People using assistive technologies

---

## 5. Do Not Use Placeholder as the Only Label

Avoid:

```html id="v8k4n3"
<input
    type="email"
    placeholder="Enter your email"
>
```

The placeholder is only a temporary hint.

Once the user starts typing, it disappears.

Prefer:

```html id="g6r2q7"
<label for="email">Email Address:</label>

<input
    type="email"
    id="email"
    name="email"
    placeholder="you@example.com"
>
```

Here:

```text id="2m9j4f"
Label       → Permanently identifies the field
Placeholder → Provides an additional hint
```

---

## 6. Use Clear Labels

Labels should describe exactly what information is expected.

Good:

```html id="j4t7pc"
<label for="phone">Phone Number:</label>
```

Less clear:

```html id="3q7k8s"
<label for="phone">Enter:</label>
```

The user should understand the purpose of the field without guessing.

---

## 7. Use Appropriate Input Types

Using the correct input type gives the browser useful information about the expected data.

Example:

```html id="r6b8yz"
<label for="email">Email:</label>
<input type="email" id="email" name="email">
```

instead of:

```html id="8h3m1k"
<label for="email">Email:</label>
<input type="text" id="email" name="email">
```

The `email` type tells the browser that an email address is expected.

Other examples:

```text id="p0e2qk"
Name     → type="text"
Email    → type="email"
Phone    → type="tel"
Age      → type="number"
Date     → type="date"
Password → type="password"
```

---

## 8. Use `required` When Necessary

If a field must be completed, use the `required` attribute.

Example:

```html id="t9x2wa"
<label for="email">Email Address:</label>

<input
    type="email"
    id="email"
    name="email"
    required
>
```

The browser can prevent the form from being submitted when the required field is empty.

Only mark fields as required when they are actually necessary.

---

## 9. Tell Users Which Fields Are Required

A form can make required fields clear through labels and instructions.

For example:

```html id="x5v7nq"
<p>Fields marked with * are required.</p>

<label for="name">Full Name *</label>
<input
    type="text"
    id="name"
    name="name"
    required
>
```

This tells the user what the `*` means.

Do not rely on color alone to communicate that a field is required.

---

## 10. Group Related Controls

Sometimes several controls belong to the same question.

For example:

```text id="4y0q7h"
Select your year:

○ First Year
○ Second Year
○ Third Year
```

These options can be grouped using `<fieldset>`.

Example:

```html id="c7p8e1"
<fieldset>

    <legend>Select your year</legend>

    <label>
        <input type="radio" name="year" value="first">
        First Year
    </label>

    <label>
        <input type="radio" name="year" value="second">
        Second Year
    </label>

    <label>
        <input type="radio" name="year" value="third">
        Third Year
    </label>

</fieldset>
```

---

## 11. The `<fieldset>` Element

`<fieldset>` groups related form controls.

Example:

```html id="z2f8a1"
<fieldset>

    ...
    
</fieldset>
```

It is especially useful for:

* Radio button groups
* Groups of checkboxes
* Related personal information
* Address sections

---

## 12. The `<legend>` Element

`<legend>` provides a description for a `<fieldset>`.

Example:

```html id="9q1x5f"
<fieldset>

    <legend>Preferred Contact Method</legend>

    <label>
        <input type="radio" name="contact" value="email">
        Email
    </label>

    <label>
        <input type="radio" name="contact" value="phone">
        Phone
    </label>

</fieldset>
```

The structure is:

```text id="1h7j4m"
<fieldset>
      ↓
Groups related controls

<legend>
      ↓
Describes the group
```

---

## 13. Example: Grouping Checkboxes

Suppose a college asks students to select their skills.

```html id="m4z6qk"
<fieldset>

    <legend>Select your skills</legend>

    <label>
        <input type="checkbox" name="skills" value="html">
        HTML
    </label>

    <label>
        <input type="checkbox" name="skills" value="css">
        CSS
    </label>

    <label>
        <input type="checkbox" name="skills" value="c">
        C Programming
    </label>

</fieldset>
```

The legend explains what all the checkboxes are about.

---

## 14. Provide Helpful Instructions

Some fields need additional information.

For example:

```text id="1y8m5s"
Password:
[________________]

Password must contain at least 8 characters.
```

HTML:

```html id="0v8h9p"
<label for="password">Password:</label>

<input
    type="password"
    id="password"
    name="password"
    aria-describedby="password-help"
>

<p id="password-help">
    Password must contain at least 8 characters.
</p>
```

The `aria-describedby` attribute associates the input with additional descriptive text.

---

## 15. `aria-describedby`

`aria-describedby` can connect a form control to additional descriptive information.

Example:

```html id="j7v2k4"
<label for="username">Username:</label>

<input
    type="text"
    id="username"
    name="username"
    aria-describedby="username-help"
>

<p id="username-help">
    Username must be between 3 and 20 characters.
</p>
```

The connection is:

```text id="f3q9w7"
aria-describedby="username-help"
                ↓
id="username-help"
```

This allows assistive technologies to associate the help text with the input.

---

## 16. Make Error Messages Clear

Suppose a user enters an invalid email address.

A vague message is:

```text id="h6m2v8"
Error!
```

A better message is:

```text id="d8p4y1"
Please enter a valid email address.
```

Good error messages should tell users:

1. What went wrong
2. How they can fix it

Example:

```html id="m3r7q9"
<label for="email">Email Address:</label>

<input
    type="email"
    id="email"
    name="email"
    aria-describedby="email-error"
    aria-invalid="true"
>

<p id="email-error">
    Please enter a valid email address.
</p>
```

---

## 17. `aria-invalid`

The `aria-invalid` attribute can communicate that a form control currently contains an invalid value.

Example:

```html id="f2p8v6"
<input
    type="email"
    id="email"
    name="email"
    aria-invalid="true"
>
```

This can be used when the application has determined that the current value is invalid.

It should reflect the actual validation state.

---

## 18. Don't Rely Only on Color

Consider this form:

```text id="5j4w7n"
Email: [wrong@email]
       ↑
      RED
```

If the only indication of an error is the red color, some users may not understand that something is wrong.

Instead, provide text:

```text id="w3r8c1"
Email: [wrong@email]

Please enter a valid email address.
```

Color can support the message, but should not be the only way information is communicated.

---

## 19. Keyboard Accessibility

A form should be usable with a keyboard.

Users should be able to move through controls using the keyboard, commonly with the **Tab** key.

For example:

```text id="k5m8z2"
Name
  ↓ Tab
Email
  ↓ Tab
Password
  ↓ Tab
Submit
```

Do not create form controls that can only be operated with a mouse.

---

## 20. Don't Remove Focus Indicators

When a user navigates using the keyboard, the browser can show which element currently has focus.

For example:

```text id="v8q3h7"
Name: [________________]
       └── Focus
```

Avoid removing focus indicators without providing an equally clear replacement.

Users need to know where keyboard focus currently is.

---

## 21. Use Logical Form Order

The HTML order should normally match the visual order.

Good:

```text id="c8w6x3"
Name
Email
Phone
Address
Submit
```

The corresponding HTML should follow the same logical sequence.

This makes keyboard navigation easier to understand.

---

## 22. Use Buttons Correctly

Use a submit button for submitting the form:

```html id="m2k7r4"
<button type="submit">Register</button>
```

Use a reset button only when resetting the form is genuinely useful:

```html id="x7v9p2"
<button type="reset">Reset</button>
```

A button should clearly communicate what it does.

Good:

```text id="9d4f1k"
Submit Application
Create Account
Send Message
```

Less useful:

```text id="1q6h7s"
Click Here
```

---

## 23. Accessible Login Form

Here is a simple accessible login form:

```html id="r8y5m2"
<form action="/login" method="post">

    <h2>Login</h2>

    <label for="email">Email Address:</label>

    <input
        type="email"
        id="email"
        name="email"
        autocomplete="email"
        required
    >

    <br><br>

    <label for="password">Password:</label>

    <input
        type="password"
        id="password"
        name="password"
        autocomplete="current-password"
        required
    >

    <br><br>

    <button type="submit">Log In</button>

</form>
```

This form has:

* Clear labels
* Correct input types
* Matching `for` and `id`
* Required fields
* Useful autocomplete information
* A clear submit button

## 25. Use Semantic HTML

Semantic elements give HTML meaningful structure.

For forms, useful elements include:

```text id="c8m2f7"
<form>
<label>
<fieldset>
<legend>
<button>
```

Using these elements provides more information than creating everything with generic `<div>` elements.

---

## 26. Avoid Unnecessary `div` Elements

This works visually:

```html id="7w5q1x"
<div>
    Name:
    <input type="text">
</div>
```

But it does not create a meaningful label relationship.

Prefer:

```html id="n5k3v8"
<label for="name">Name:</label>

<input
    type="text"
    id="name"
    name="name"
>
```

Semantic HTML makes the purpose and relationships clearer.

---

## 27. Use Autocomplete Correctly

Autocomplete can make forms faster to complete.

Example:

```html id="7h3v5m"
<input
    type="email"
    id="email"
    name="email"
    autocomplete="email"
>
```

Another example:

```html id="p4j6q8"
<input
    type="text"
    id="name"
    name="name"
    autocomplete="name"
>
```

Useful autocomplete values include:

```text id="9z6t4y"
name
email
tel
username
current-password
new-password
```

These values help browsers understand what information a field represents.

## 28. Real-World Example: College Application Form

Imagine a college application form.

```text id="5x7q9m"
College Application

Full Name
[________________________]

Email Address
[________________________]

Phone Number
[________________________]

Course
[________________________]

Upload Certificate
[ Choose File ]

☐ I confirm that the information is correct.

[ Submit Application ]
```

A semantic HTML structure could be:

```html id="n4j8q2"
<form action="/apply" method="post">

    <h2>College Application</h2>

    <label for="name">Full Name:</label>
    <input
        type="text"
        id="name"
        name="name"
        autocomplete="name"
        required
    >

    <label for="email">Email Address:</label>
    <input
        type="email"
        id="email"
        name="email"
        autocomplete="email"
        required
    >

    <label for="phone">Phone Number:</label>
    <input
        type="tel"
        id="phone"
        name="phone"
        autocomplete="tel"
        required
    >

    <label for="certificate">Upload Certificate:</label>
    <input
        type="file"
        id="certificate"
        name="certificate"
    >

    <label>
        <input
            type="checkbox"
            name="confirm"
            required
        >
        I confirm that the information is correct.
    </label>

    <button type="submit">
        Submit Application
    </button>

</form>
```

## 29. Accessibility Checklist

Before completing a form, check:

```text id="8q3k1m"
✓ Does every important input have a clear label?
✓ Does each label connect to the correct input?
✓ Is the correct input type being used?
✓ Are required fields clearly identified?
✓ Are related controls grouped?
✓ Does a radio group have a meaningful legend?
✓ Are instructions provided when necessary?
✓ Are error messages clear?
✓ Are errors communicated without relying only on color?
✓ Can the form be used with a keyboard?
✓ Is keyboard focus visible?
✓ Are buttons clearly named?
✓ Is the form order logical?
```

## 30. Quick Reference

| Element / Attribute | Purpose                                   |
| :------------------ | :---------------------------------------- |
| `<label>`           | Describes a form control                  |
| `for`               | Connects a label to an input's `id`       |
| `id`                | Identifies the form control               |
| `<fieldset>`        | Groups related controls                   |
| `<legend>`          | Describes a fieldset                      |
| `required`          | Makes a field required                    |
| `aria-describedby`  | Associates additional descriptive text    |
| `aria-invalid`      | Indicates an invalid control state        |
| `autocomplete`      | Helps browsers understand and fill fields |
| `<button>`          | Creates an interactive button             |

## 31. Easy Way to Remember

Think about an accessible form as:

```text id="k9r3w5"
LABEL
  ↓
INPUT
  ↓
HELP / INSTRUCTIONS
  ↓
VALIDATION
  ↓
CLEAR BUTTON
```

For groups:

```text id="p6x2m8"
<fieldset>
      ↓
<legend>
      ↓
Related controls
</fieldset>
```

The goal is simple:

> **The user should always know what to enter, where to enter it, and how to fix a mistake.**

---

## Key Points

* Accessible forms should be usable by people with different abilities.
* Every important form control should have a clear `<label>`.
* Connect labels and inputs using matching `for` and `id` values.
* Do not use placeholder text as the only label.
* Use the correct input type for the expected information.
* Use `required` for fields that must be completed.
* Clearly explain which fields are required.
* Use `<fieldset>` and `<legend>` to group related controls.
* Use `aria-describedby` when additional instructions need to be associated with a control.
* Use `aria-invalid` when a control has been identified as invalid.
* Error messages should explain what went wrong and how to fix it.
* Do not rely only on color to communicate errors or required fields.
* Forms should be usable with a keyboard.
* Keep keyboard focus visible.
* Keep the form's structure and navigation order logical.
* Use clear button names such as `Submit Application` instead of vague text such as `Click Here`.
* Use semantic HTML instead of unnecessary generic elements.
* Use appropriate `autocomplete` values where useful.
